# Модульный движок заполнения тендерных таблиц

## Назначение

Конвейер разделён на независимые этапы:

`DOCX/PDF -> извлечение строк -> идентификация изделия -> шаблон инженера -> данные 1БП/data_tenders -> явное требование ТЗ -> GigaChat только для остатка -> валидация -> запись -> audit -> обучение БЗ после закрытия Word`.

Цель архитектуры — не «угадать соседнюю строку», а сохранить физическую идентичность каждой строки: `table_index + row_index + target_cell_index + number + field_key + parent_context`.

## Приоритет источников

1. Существующий ответ сохраняется, если `TENDER_OVERWRITE_EXISTING=0`.
2. Ранее исправленный инженером шаблон БЗ имеет приоритет над генерацией.
3. Факты изделия из `data_tenders`/ТУ используются для параметров самого изделия.
4. Явно заданные значения из колонки «Требования» используются для конфигурационных требований.
5. GigaChat вызывается только для реально неразрешённых строк.
6. Любой результат AI проходит типовую и межполюсную валидацию перед записью.

AI не получает права переносить значение по «похожему названию». В JSON цель имеет обязательный `id`; родительская обмотка также входит в идентичность.

## Почему исправлен старый алгоритм

В Word заголовок колонки ответа часто объединён. Поэтому его физический индекс нельзя напрямую использовать для каждой строки. Для тендерной таблицы движок заново вычисляет структуру каждой строки: требование — предпоследняя физическая ячейка, ответ — последняя; вложенные строки распознаются как `[№, родитель, параметр, требование, ответ]`.

Это устраняет ошибки вида:

- `40 15` в строках 5.5–5.7;
- масса `297 302 317 252` в строке 11.1;
- `от 0,11 до 0,15` в строке 12.2;
- название изготовителя в строках 12.5/17.3;
- смешивание одинаковых «Класс точности» и «Номинальная нагрузка» разных обмоток.

## Правила для эталона 6a / ТРГ-УЭТМ-110

Эталонный документ инженера используется как доверенный шаблон после сохранения/закрытия файла. При первом заполнении факты берутся из локального `data_tenders` и из требований.

Для 110 кВ из 1БП.769.001 поддержаны в том числе: 126 кВ максимального рабочего напряжения, 2123/819, масса 297 кг по исполнению с фарфоровым изолятором, 450 кВ грозового импульса, 200 кВ одноминутного испытательного напряжения, 0,7 МПа, SF6 1,5 кг + N2 0,6 кг и срок службы не менее 40 лет.

При наличии исправленного шаблона инженера его значения имеют более высокий приоритет. Поэтому, например, значение срока службы 30 лет из эталона 6a не заменяется автоматически на 40 лет из ТУ: оно считается результатом фактически принятого инженером варианта.

## Маркеры

- `**` ставится только для значения, которое реально выдала AI.
- Значения из БЗ/шаблона/data_tenders не получают `**`.
- Значения, прямо взятые из требования ТЗ, не помечаются как AI.
- Если требование содержит только `*`, детерминированный слой не выдумывает значение.

## Обучение БЗ

`DocumentTracker` отслеживает сохранения Word, ждёт стабилизации файла и проверяет наличие lock-файла `~$...`. Обучение происходит после фактического закрытия Word и только один раз за цикл наблюдения.

В БЗ сохраняются только итоговые значения без AI-маркеров `**`. Поэтому следующее совпадающее техническое задание сначала обслуживается из шаблона и может вообще не обращаться к GigaChat.

## PDF

PDF выделен в отдельный модуль `services/tender_engine/pdf_pipeline.py`. Он использует координаты строки, OCR как fallback и Vision/AI только для остатка. Общий resolver/validator используется тот же, что и для DOCX. Это принципиально важно: PDF не должен иметь отдельную бизнес-логику подбора значений.

## Структура

- `schema.py` — единые модели строки/решения/контекста.
- `text.py` — нормализация, числа, маркеры.
- `rules.py` — явное сопоставление параметра с canonical `field_key`.
- `docx_reader.py` — физический разбор Word-таблицы.
- `context.py` — тип изделия/напряжение.
- `data_source.py` — локальные ТУ/data_tenders.
- `template_store.py` — доверенные шаблоны инженеров.
- `requirements.py` — безопасное извлечение явного ответа из ТЗ.
- `resolver.py` — приоритет источников.
- `validator.py` — типы, диапазоны и защита от переноса чужого значения.
- `ai.py` — пакетный GigaChat для неразрешённых строк.
- `writer.py` — запись строго в сохранённую физическую ячейку.
- `pipeline.py` — полный DOCX-конвейер и audit.
- `pdf_pipeline.py` — PDF-конвейер.

Старые точки входа (`search_docx_AI.py`, `data_tenders_knowledge.py`, `template_knowledge.py`, `search_pdf_AI.py`) оставлены тонкими фасадами, чтобы текущий GUI и `main.py` не пришлось переписывать целиком.

- 86/86 семантических значений совпадают с эталоном;

- без шаблона автоматически заполняются 83/86 строк;
