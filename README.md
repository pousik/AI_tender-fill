# Гибридный модуль автозаполнения тендерных DOCX/PDF

Автозаполнение технических требований (ТРГ/трансформаторы тока) в тендерных
документах DOCX и PDF. Модуль сочетает детерминированный алгоритм (база
знаний в SQLite) с проверкой нейросетью GigaChat, которая видит весь
контекст документа.

## Архитектура (единая для DOCX и PDF)

1. **Определение типа оборудования** — детерминированно по БД и параметрам
   документа (`_determine_type` / `match_tr_type_by_pdf_rules`).
2. **Алгоритмический проход** — для каждой строки ищется канонический ключ
   параметра (`FieldRule`) и берется значение из расширяемой базы знаний
   (`KnowledgeEntry`) или из исторических справочников (`TrTypeRule` и
   связанные таблицы). Такие значения — **константы**, они не помечаются.
3. **AI-заполнение пустых полей** — если после БД-прохода поле осталось
   пустым, GigaChat получает контекст документа, прежде всего значение
   требования слева, соседние строки и связанные параметры. Даже если слева
   стоит `*` или поле требования пустое, это не запрещает определить ответ
   по контексту. Для значения, которого нет в БД, программа ставит `**`; если
   в левой колонке требования уже есть `*`, ставится только одна `*`.
4. **Порционная обработка** — большие DOCX/PDF не отправляются одним огромным
   запросом: строки для AI обрабатываются небольшими порциями. Это уменьшает
   размер каждого запроса и устраняет типичный `read operation timed out`.
   Для GigaChat также задан увеличенный сетевой таймаут и автоматические
   повторы временных ошибок.
5. **Аудит** — рядом с результатом создается `<output>.audit.json`:
   источник, уверенность и причина решения по каждой строке.

Изготовитель и заводской тип/марка являются константами БД и заполняются
даже тогда, когда в требуемом значении слева стоит `*`; для них маркеры не
ставятся. Значения из БД (напряжение, климат, классы точности и другие
справочные константы) также всегда записываются без `**`.

Итог: в выходном файле сразу видно, какие значения — гарантированные
константы из БД, а какие выведены нейросетью по контексту и помечены маркером.
Если надежного вывода нет, ячейка остается пустой — никаких
`Не определено по ТЗ`, `***` и других заглушек.

## Установка

```bash
pip install -r requirements.txt
```

Для PDF дополнительно нужен Tesseract OCR с русским языковым пакетом:

```bash
tesseract --list-langs   # в списке должен быть `rus`
```

Если `tesseract` не в PATH (Windows):

```powershell
$env:TESSERACT_CMD = "C:\Program Files\Tesseract-OCR\tesseract.exe"
```

## Запуск

```powershell
./run.ps1 "входной_файл.docx" "выходной_файл.docx"

Для старого Word `.doc` можно указывать исходный файл напрямую:
`./run.ps1 "входной_файл.doc" "выходной_файл.doc"`. На Windows сначала используется установленный Microsoft Word через `pywin32`; если его нет — LibreOffice.
```

`run.ps1` запрашивает ключ GigaChat через SecureString (никогда не
записывает его на диск), затем проверяет подключение (`test_gigachat.py`)
и запускает `main.py`.

Либо напрямую:

```bash
set GIGACHAT_CREDENTIALS=ВАШ_КЛЮЧ
python main.py "входной_файл.pdf" "выходной_файл.pdf"
```

Переменные окружения: `GIGACHAT_CREDENTIALS` (обязательна),
`GIGACHAT_MODEL` (по умолчанию `GigaChat-2`), `GIGACHAT_SCOPE`
(`GIGACHAT_API_PERS`), `GIGACHAT_BASE_URL`, `GIGACHAT_VERIFY_SSL_CERTS`,
`GIGACHAT_TIMEOUT` (`180` секунд), `GIGACHAT_MAX_RETRIES` (`2`),
`AI_CONFIDENCE_THRESHOLD` (`0.75` для замены уже имеющихся не-БД значений),
`OCR_DPI` (`300`), `OUTPUT_DPI` (по умолчанию равен `OCR_DPI`), `TESSERACT_CMD`,
`TESSERACT_LANG` (`rus+eng`), `TESSERACT_PSM` (`6`).

### Приоритет результата GigaChat

Для каждой строки действует правило: подтверждённая база данных (`project_base`, `knowledge_db`, `legacy_db`) имеет абсолютный приоритет. Значение `HEURISTIC`/`REQUIREMENT` считается только предварительной подсказкой; если GigaChat возвращает уверенный `AI_CONTEXT` (по умолчанию confidence >= `0.75`), в итоговый документ записывается именно ответ модели и добавляется `**` (или `*`, если требование уже отмечено звёздочкой). В `.audit.json` сохраняются `algorithm_value`, `ai_value`, `final_value` и `decision`, поэтому причину выбора можно проверить для каждой строки.

Если в исходном документе уже есть заполненный ответ, по умолчанию он сохраняется. Для принудительной перезаписи используется `TENDER_OVERWRITE_EXISTING=1`.

## PDF: как это работает

PDF намеренно не конвертируется в DOCX и обрабатывается на месте:

1. текст извлекается вместе с координатами (PyMuPDF);
2. отсканированные страницы распознаются Tesseract OCR, если у страницы
   нет полезного текстового слоя;
3. логические строки таблицы восстанавливаются по геометрии (границы
   таблицы, а не только по номеру строки — в исходных чертежах несколько
   физических строк могут иметь одну общую ячейку номера);
4. к каждой строке применяется тот же гибридный алгоритм+AI пайплайн, что
   и для DOCX;
5. ответы вписываются в колонку участника без пересборки PDF — файл
   сохраняется как независимая копия, отсканированные страницы
   "расплющиваются" в чистое изображение перед записью, чтобы убрать
   возможный битый/невидимый OCR-слой исходного скана.

**Важное ограничение**: если в присланном PDF физически нет колонки для
ответа участника, программа не должна её угадывать — такой документ нужно
поддержать отдельным шаблоном координат либо оформить как приложение.

## База знаний: как нарастить без правки кода

Таблица `knowledge_entries` — единственная точка роста БЗ. Поля: категория,
ключ, значение, алиасы, тип трансформатора, напряжение, источник,
комментарий. Любой новый параметр добавляется без изменения схемы/кода.

Ручное добавление:

```powershell
python tools/add_knowledge.py --key nominal_current --value "500-1000" --tr-type ТРГ --voltage 110 --source passport
```

Пакетный импорт:

```powershell
python tools/add_knowledge.py --json knowledge_seed.json
```

Существующая БД при этом не удаляется — инициализация проекта (`bootstrap.py`)
не разрушает уже накопленные записи.

Таблица `field_rules` сопоставляет реальные формулировки строк ТЗ
("Номинальное напряжение обмотки, кВ") с каноническим ключом БЗ
(`nominal_voltage`), так что документы с разной формулировкой одного и того
же параметра распознаются одинаково — этот справочник тоже расширяется
через `knowledge_seed.json`/`add_knowledge.py`, без изменения Python-кода.

### Подтверждение AI-значения

После ручной проверки аудита найденное нейросетью значение можно перенести
в БЗ как константу — работает и для DOCX-, и для PDF-аудита (единый формат):

```powershell
python tools/promote_audit.py "Заполненный_файл.docx.audit.json" --id item_17 --key sf6_pressure
```

После подтверждения следующий запуск использует это значение уже на первом,
детерминированном проходе, и `**` для него больше не потребуется.

## Формат маркировки

- Без суффикса — значение взято из базы знаний/справочника как константа,
  либо подтверждено нейросетью без изменений (`source: "DB"`).
- Суффикс `**` — значение выведено нейросетью из контекста документа, а не
  из БД (`source: "AI_CONTEXT"`), и требует проверки человеком. Если в
  требуемом значении слева уже есть `*`, используется одна `*`, чтобы не
  получить `***`/`****`.
- Изготовитель и заводской тип/марка, а также любые подтвержденные БД
  константы, никогда не получают маркер.
- В `<output>.audit.json` по каждой строке видно `algorithm_value` (что дал
  первый проход), `final_value` (итог после AI-аудита), `source`, `mark`,
  `confidence`, `reason`.

## Безопасность

Ключ GigaChat никогда не хранится в файлах проекта. `run.ps1` запрашивает
его через `SecureString` и передает только переменной окружения текущего
процесса. Если ключ ранее был закоммичен в код — его нужно отозвать и
перевыпустить.

## Что было исправлено при ревизии

- **DOCX AI-промпт**: служебный объект `python-docx._Cell` больше не попадает в `json.dumps`; для нейросети формируется отдельное JSON-сериализуемое представление строк.
- **Определение напряжения DOCX**: исправлено ошибочное использование `rstrip('.0')`, которое могло превращать `110` в `11`; добавлено извлечение напряжения из общего контекста документа.
- **Приоритет источников**: эвристические значения больше не объявляются `DB` только потому, что AI их подтвердил; `DB` сохраняется только для реальных записей БЗ/справочников.
- **Существующие ответы DOCX**: уже заполненная ячейка участника не стирается, если новый запуск не получил доказательного значения.
- **DOCX оформление**: запись ответа выполняется с сохранением структуры/базового форматирования ячейки вместо безусловного `cell.text = ...`.
- **PDF определение типа**: вместо выбора первого подходящего правила используется оценка признаков и явная обработка неоднозначности.
- **PDF OCR-таблица**: первая физическая строка больше не отбрасывается безусловно; пропускаются только распознанные заголовки и действительно пустые строки.
- **Константы PDF/DOCX**: изготовитель и заводской тип/марка сначала берутся непосредственно из БД и не могут быть заменены AI.
- **Легаси-справочники**: убрано опасное `rstrip("1")` для сравнения значений; специальное послабление `УХЛ` ↔ `УХЛ1` оставлено только для климатического исполнения.
- **GigaChat JSON**: ответ проверяется на JSON-объект; неверный тип ответа теперь диагностируется явно. Поддерживается случай, когда пользователь случайно передал ключ с префиксом `Bearer `.

- **`tools/add_knowledge.py`**: путь к БД вычислялся от каталога `tools/`
  вместо корня проекта — CLI молча писал знания в несуществующий файл, а
  не в реальную `transformers.db`. Исправлено.
- **PDF-модуль не использовал расширяемую базу знаний** (`KnowledgeEntry`/
  `FieldRule`) — работал только по жестко зашитым легаси-справочникам, из-за
  чего рост БЗ (`add_knowledge.py`) не влиял на заполнение PDF. Добавлен
  такой же алгоритмический проход, как в DOCX.
- **Несогласованная и небезопасная семантика `**`**: в PDF-модуле `**`
  раньше означал "значение противоречит требованию", а в DOCX — "значение
  выведено нейросетью из контекста". Приведено к единому смыслу, как просил
  заказчик: `**` только для контекстных AI-выводов, не подтвержденных БД.
- **AI-подсказки принимались без проверки уверенности**: для уже имеющихся
  не-БД значений сохранен порог `AI_CONFIDENCE_THRESHOLD`; для пустых полей
  AI теперь обязан предложить лучший контекстный ответ и пометить его `**`,
  а `confidence` сохраняется в аудите для последующей проверки.
- **GigaChat timeout на больших документах**: SDK раньше создавался без явного
  `timeout`, поэтому использовалось короткое значение по умолчанию. Добавлен
  `GIGACHAT_TIMEOUT=180`, повтор временных HTTP-ошибок и порционная отправка
  пустых строк.
- **Пустые поля после AI**: если модель не смогла надежно вывести конкретную
  характеристику, ячейка остается пустой; текстовые заглушки не вставляются.
  `required_val="*"` и пустой `required_val` не блокируют контекстное AI-заполнение.
- **PDF-модуль не писал `.audit.json`** — в отличие от DOCX, что делало
  `tools/promote_audit.py` неприменимым к PDF-документам. Добавлено, в
  едином формате с DOCX.
- **Фатальный сбой на строках-заголовках**: если алгоритм/AI не находили
  значение для строки-заголовка раздела (пустое значение — ожидаемое
  поведение), весь процесс падал с ошибкой "не удалось определить значения".
  Теперь такие строки не считаются ошибкой, а реально нерешенные строки
  попадают в `unresolved_rows` аудита, не прерывая обработку.
- **Опечатка в дефолте DPI OCR**: код документировал 300 DPI, а по факту
  использовал 100 DPI, если `OCR_DPI` не задана явно. Исправлено.
- **Мертвый код**: `canonicalize_field(None, param_name) if False else None`
  в DOCX-модуле — не имеющая смысла конструкция, всегда дающая `None`;
  убрана.
- **Дублирование кода GigaChat** между DOCX- и PDF-модулями (авторизация,
  разбор ответа, JSON-парсинг) вынесено в общий `services/gigachat_client.py`.
- **Убрано лишнее**: legacy `services/search_docx.py` (не-AI версия,
  дублирующая функциональность без БЗ и без AI-аудита, нигде не
  используется), дублирующийся `test.py` (точная копия `test_gigachat.py`),
  черновая заметка `123.txt` и хронологические `PDF_FIX.md`/`PDF_SUPPORT.md`
  — все объединено в этот README.
- Тестовые тендерные документы пользователя (файлы `.pdf`/`.docx` с
  реальными названиями объектов) исключены из поставки модуля — это данные,
  а не код; при необходимости положите их рядом с `main.py` для запуска.


## Поддержка DOC

Старый бинарный формат `.doc` не читается библиотекой `python-docx` напрямую.
Модуль автоматически преобразует `.doc` во временный `.docx`, выполняет существующий
гибридный Word-процессор и затем сохраняет итог обратно в `.doc`. На Windows
приоритетно используется Microsoft Word (COM), что дает наилучшую совместимость
со старыми документами; LibreOffice используется как резервный конвертер.

Важно: GUI-фильтр файлов в этой версии не ограничивает формат `.doc`, потому что
в архиве отсутствует отдельный графический загрузчик — единой точкой входа является `main.py`.

## Контекстный режим заполнения (v4)

В v4 значение `required_val` рассматривается как требование заказчика, а не как готовый ответ участника. Для строк без подтвержденной БД GigaChat должен сопоставлять тип изделия, напряжение, соседние и повторяющиеся строки, связанные характеристики и примеры уже заполненных документов из `test_documents`.

Для `source=AI_CONTEXT` модель обязана возвращать `evidence` — идентификаторы строк текущего документа или название использованного примера. Программный слой дополнительно отбрасывает очевидные противоречия (например, наибольшее напряжение ниже номинального) и механический повтор порога `не менее/не более/в соответствии с...` без отдельного основания.

Заголовки разделов, которые в Word физически занимают все колонки, теперь не считаются строками для заполнения.

## v6: оптимизированный контекстный AI-проход

- Все однозначные значения из самого документа заполняются без AI.
- Для оставшихся пустых полей выполняется **один** запрос GigaChat вместо пачки запросов с повторением глобального контекста.
- В AI передаются все извлечённые факты документа в компактном формате `id|номер|параметр|значение`, поэтому факт, указанный ранее на другой странице/в другой таблице, доступен модели.
- Локальный `nearby/related` контекст больше не дублируется для каждого поля.
- Требуемое значение не считается фактическим значением и не копируется автоматически.
- Если надежного факта нет, AI обязан вернуть пустое значение.
- `evidence` указывает на строку документа, на которой основан вывод.
- `TENDER_VERIFY_GIGACHAT=1` включает отдельную диагностическую проверку API; по умолчанию она выключена.

## Новая гибридная БЗ

Порядок заполнения DOCX теперь такой:

1. `KnowledgeEntry` / `FieldRule` — точечные знания и константы.
2. Шаблонная БЗ (`tenders` + `tender_parameters`) — поиск ранее сохраненного похожего тендера.
3. Профиль по напряжению (`parameter_profiles` + `profile_parameters`).
4. Контекст самого документа.
5. GigaChat — только для реально оставшихся пустых полей.

Если значение найдено в БЗ или шаблоне, соответствующая строка не передается в AI.

После сохранения DOCX текущие доверенные значения автоматически добавляются в шаблонную БЗ. Строки с маркером `**` не сохраняются. При закрытии GUI дополнительно выполняется захват уже сохраненного DOCX без запуска AI.

Старая база `tender.db` импортируется в `transformers.db` при первом запуске, если шаблоны еще отсутствуют.
