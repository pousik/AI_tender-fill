# Логика заполнения тендерных таблиц

## Источники

1. `transformers.db` — ранее исправленные инженером шаблоны. Используется до AI.
2. `data_tenders/tenders.db` — структурированная техническая БД: классы напряжения, изоляция, климат, классы точности, габариты, массы и связанные справочные значения.
3. `data_tenders/.data_tenders_index.json` — быстрый индекс исходных ТУ/РЭ. Используется для характеристик, которых нет в нормализованных таблицах.
4. Текущее ТЗ — источник точного требования, когда оно не противоречит типу поля.
5. GigaChat — только для оставшихся нерешённых/нетипичных/хаотичных полей.

## Порядок заполнения

`читаем DOCX -> определяем изделие и напряжение -> ищем исправленный шаблон -> ищем точное значение в data_tenders -> берём явное требование ТЗ для разрешённых полей -> AI для остатка -> валидация -> запись в физическую ячейку`.

AI не заменяет детерминированный слой и не получает права перезаписывать уже найденные значения.

## Идентификация строки

Каждая строка имеет независимый якорь:

- таблица;
- номер строки ТЗ;
- физический индекс ячейки ответа;
- canonical `field_key`;
- родительский контекст, например `Обмотка 1`, `Обмотка 2`, `Обмотка 3-6`.

Повторяющиеся строки (`Класс точности`, `Номинальная нагрузка`) не сопоставляются только по названию.

## AI-поля

Если детерминированный слой не нашёл надёжного значения, строка передаётся AI вместе с полным контекстом текущего документа и компактным контекстом `data_tenders`.

Значение, принятое от AI, записывается с маркером `**` (для обязательных `*` — `*`) и дополнительно подсвечивается жёлтым в Word. Значения из БД/шаблона/явного требования жёлтым не подсвечиваются.

## Безопасность от сдвига

Писатель изменяет только физическую ячейку, зафиксированную reader-ом. Значения составных источников сначала разбираются по смыслу: например, `40 15` разделяется на скорость ветра без гололёда и при гололёде.

Валидация после AI блокирует значения неправильного типа, переносы масс/давлений/ветра в другие поля и конфликтующие связанные параметры.

## Обучение

После редактирования инженером финальный документ можно передать через `capture_final_docx`. В шаблонную БД сохраняются только подтверждённые значения без `**`; они используются при следующих заполнениях раньше AI.

## PDF-конвейер

PDF обрабатывается отдельно от DOCX и не конвертируется в Word перед заполнением.

`PDF -> текстовый слой/ OCR -> геометрия таблицы -> физические ячейки -> DataTenders/ТЗ -> AI -> валидация -> точечная запись в PDF`.

Reader больше не вычисляет колонку ответа по фиксированным долям страницы. Сначала ищется реальная вертикальная сетка технической таблицы, затем горизонтальные границы строк. Для многострочных строк используется вся высота ячейки, поэтому перенос строки внутри параметра не создаёт новую ложную строку.

Для сканированных PDF Tesseract получает предварительно очищенное от линий изображение. Это уменьшает склейку текста с границами таблицы. Если векторной сетки нет, линии таблицы ищутся по растровому изображению.

В PDF запись выполняется только внутри внутренней области конкретной ячейки ответа. Для кириллицы используется системный TrueType-шрифт (на Windows в первую очередь Arial/Calibri). AI-значения получают жёлтую заливку ячейки и маркер `**`/`*`.

Параметр `--no-ocr` теперь отключает только OCR. Он не отключает GigaChat.
